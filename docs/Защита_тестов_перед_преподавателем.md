# Защита тестов проекта NoteTag

## Короткие ответы на основные вопросы

### TypeScript остался основным языком

Да, для backend. Сервер NoteTag написан на NestJS и TypeScript. TypeScript не является языком базы данных: база работает на PostgreSQL, а запросы к ней выполняются на SQL через TypeORM и драйвер `pg`.

Стек проекта по слоям:

- frontend — React и JavaScript;
- backend — NestJS и TypeScript;
- база данных — PostgreSQL;
- миграции — SQL-команды внутри TypeScript-класса;
- тестовый раннер — Vitest.

### На чём написаны тесты

Почти все тесты написаны на TypeScript в файлах `*.spec.ts`. Единственный файл на JavaScript — `frontend/src/api/notetag.test.js`, потому что сам frontend проекта написан на JavaScript.

Все группы тестов запускает Vitest:

- unit-тесты используют `vi.fn`, `expect`, `describe` и `it`;
- HTTP-тесты используют Vitest, Nest TestingModule и Supertest;
- тесты PostgreSQL используют Vitest и реальное соединение через `pg`.

### Нужны ли e2e-тесты

Удалять их не обязательно. Они вынесены в отдельную команду и не мешают unit-тестам.

В проекте это три небольших теста HTTP-слоя авторизации. Они проверяют, что запрос действительно проходит через маршрутизацию NestJS и `ValidationPipe`:

- правильная регистрация возвращает HTTP 201;
- неправильный DTO возвращает HTTP 400;
- вход возвращает HTTP 200 и `accessToken`.

Важно говорить честно: это облегчённый HTTP e2e-тест, потому что `AuthService` в нём заменён мок-объектом. Он проверяет HTTP-контракт приложения, но не проходит до реальной базы данных. Полная проверка БД выполнена отдельно.

Если преподаватель просил только unit-тесты, сначала показывай `npm test`. E2E можно представить как дополнительную проверку и запускать только по вопросу преподавателя командой `npm run test:e2e`.

### Где находятся тесты PostgreSQL

Они находятся в отдельном файле:

```text
test/database.integration-spec.ts
```

Это не отдельная физическая папка, но отдельный набор тестов и отдельная конфигурация:

```text
vitest.db.config.mts
```

Они запускаются только командой `npm run test:db`, поэтому обычные unit-тесты не зависят от PostgreSQL. Такое разделение важнее отдельной папки: unit-run остаётся быстрым, а ошибка соединения с БД не маскируется под ошибку бизнес-логики.

## Готовый текст для защиты

Можно рассказать почти дословно:

> Backend проекта написан на TypeScript, база данных — PostgreSQL. Для тестирования я использовал Vitest. Я разделил проверки на три уровня. Первый уровень — unit-тесты: сервисы и контроллеры проверяются изолированно, а TypeORM-репозитории заменяются моками через vi.fn. Второй уровень — HTTP-тесты: они проверяют маршрутизацию NestJS, валидацию DTO и HTTP-статусы. Третий уровень — интеграционные тесты PostgreSQL: они подключаются к отдельной базе и проверяют реальные UNIQUE, CASCADE, NOT NULL, FOREIGN KEY и DEFAULT ограничения.
>
> Такое разделение нужно, потому что unit-тест должен быть быстрым и точно показывать ошибку в одном классе. Проверку ограничения базы нельзя надёжно выполнить моками, поэтому для неё используется настоящая PostgreSQL. HTTP-тест нужен, чтобы проверить поведение запроса между маршрутом, ValidationPipe и контроллером.
>
> Сейчас проходят 68 unit-тестов, 3 HTTP e2e-теста и 5 тестов базы данных. Покрытие unit-контура составляет 99,37 процента statements, 84,61 процента branches, 100 процентов functions и 100 процентов lines. Дополнительно проходят TypeScript-сборка и ESLint.

## Как провести демонстрацию

### Шаг 1 Показать команды

Открой `package.json` и покажи scripts:

```json
"test": "vitest run",
"test:watch": "vitest",
"test:cov": "vitest run --coverage",
"test:e2e": "vitest run --config vitest.e2e.config.mts",
"test:db": "vitest run --config vitest.db.config.mts"
```

Скажи: каждая команда отвечает за свой уровень, поэтому можно понять, где именно произошёл сбой.

### Шаг 2 Запустить unit-тесты

```bash
npm test
```

Ожидаемый результат: 16 файлов и 68 пройденных тестов.

Пояснение: здесь нет реального HTTP-порта и подключения к PostgreSQL. Зависимости заменены управляемыми моками.

### Шаг 3 Показать один простой unit-тест

Открой `src/users/users.service.spec.ts` и покажи сценарий дублирования логина.

Что сказать:

1. `repository.save` заменён функцией `vi.fn`.
2. `mockRejectedValue` имитирует PostgreSQL-ошибку с кодом `23505`.
3. Вызывается настоящий метод `UsersService.createClient`.
4. Проверяется преобразование технической ошибки БД в `ConflictException`.

Смысл: unit-тест проверяет собственную логику сервиса, а не PostgreSQL.

### Шаг 4 Показать отрицательный сценарий доступа

Открой `src/notes/notes.service.spec.ts` и покажи тест `does not allow ... of another client note`.

Что сказать: репозиторий возвращает `null`, как будто заметка не принадлежит текущему пользователю. Для чтения, изменения и удаления сервис должен вернуть `NotFoundException`. Это предотвращает доступ одного клиента к данным другого.

### Шаг 5 Показать DTO

Открой `src/common/dto/validation.spec.ts`.

Что сказать: TypeScript проверяет типы во время компиляции, но пользовательский JSON приходит во время выполнения. Поэтому декораторы `class-transformer` и `class-validator` тестируются отдельно через `plainToInstance` и `validate`.

### Шаг 6 Показать покрытие

```bash
npm run test:cov
```

В `vitest.config.mts` установлены минимальные пороги:

- statements — 95%;
- branches — 80%;
- functions — 95%;
- lines — 95%.

Не говори, что 100% покрытия гарантирует отсутствие багов. Правильная формулировка: покрытие показывает, какой код был выполнен тестами, но качество проверок определяется сценариями и ожиданиями.

### Шаг 7 Показать PostgreSQL

```bash
npm run test:db
```

Перед демонстрацией база `notetag_acceptance` должна существовать, а миграция должна быть применена.

Что сказать: каждый тест начинает транзакцию через `BEGIN` и заканчивает `ROLLBACK`, поэтому тестовые строки не остаются в базе.

### Шаг 8 E2E показывать при необходимости

```bash
npm run test:e2e
```

Объяснение в одной фразе: unit-тест вызывает метод класса напрямую, а HTTP e2e отправляет настоящий запрос `POST /auth/register` или `POST /auth/login` через сервер NestJS и проверяет статус ответа.

## Как устроены моки

Пример минимального репозитория:

```ts
const repository = {
  create: vi.fn(),
  save: vi.fn(),
};

const service = new UsersService(
  repository as unknown as Repository<User>,
);
```

Почему не создаётся настоящий `Repository<User>`: unit-тесту нужны только методы, которые вызывает `UsersService`. Реальный репозиторий подключил бы базу и превратил бы unit-тест в интеграционный.

Основные методы Vitest:

- `vi.fn()` — создаёт мок-функцию и записывает её вызовы;
- `mockReturnValue` — задаёт обычный результат;
- `mockResolvedValue` — возвращает успешный Promise;
- `mockRejectedValue` — возвращает отклонённый Promise;
- `toHaveBeenCalledWith` — проверяет аргументы вызова;
- `rejects.toBeInstanceOf` — проверяет ожидаемую асинхронную ошибку;
- `vi.clearAllMocks()` — очищает историю между тестами.

## Что проверяет каждый тест PostgreSQL

### Уникальность логина

Два пользователя с одинаковым `users.login` не должны создаваться. Ожидается SQLSTATE `23505` и constraint `UQ_users_login`.

### Каскадное удаление

После удаления пользователя должны исчезнуть его заметки, теги и связи `note_tags`. Ожидаемые количества — ноль.

### Обязательное поле

Заметка с `content = NULL` не должна создаваться. Ожидается SQLSTATE `23502` для столбца `content`.

### Внешний ключ

Заметка не может ссылаться на несуществующего пользователя. Ожидается SQLSTATE `23503` и constraint `FK_notes_user`.

### Значение по умолчанию

Если роль пользователя не передана, PostgreSQL должен сохранить `role = 'client'` и автоматически заполнить `created_at`.

## Частые вопросы преподавателя

### Почему Vitest, а не Jest

Vitest даёт знакомый Jest-подобный API, быстро запускает TypeScript-тесты и поддерживает V8 coverage. Для этого проекта он используется единообразно для unit, HTTP и PostgreSQL тестов.

### Почему репозиторий приводится через unknown

Потому что тест создаёт минимальный объект, а не полный TypeORM Repository. `unknown` обозначает явную границу тестового дубля и не отключает проверку типов во всём файле, как `any`.

### Чем unit-тест отличается от DB-теста

Unit-тест заменяет Repository моками и проверяет только класс. DB-тест отправляет настоящий SQL в PostgreSQL и проверяет реальные constraint-коды.

### Почему тестируем и успешные, и ошибочные сценарии

Большая часть рисков находится в отрицательных ветках: чужая заметка, неправильный пароль, повторный логин, пустой content и отсутствующий внешний ключ.

### Что было найдено тестированием

Был найден дефект запуска миграции: широкий шаблон TypeORM захватывал файл `*.spec.ts` как миграцию. Конфигурация заменена явным импортом класса миграции, после чего миграция и пять DB-тестов прошли успешно.
